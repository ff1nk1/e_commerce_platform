# ADR 0006. Слои внутри сервиса и место саг

## Контекст

Семь сервисов выросли по-разному, и `app/` успел разойтись: где-то сценарии лежат в `Services`, где-то в `Kafka`, саги — в `Kafka/Saga` (catalog) и `Messaging` (order). При переносе кода непонятно, куда класть долгоживущий сценарий (сагу), а куда — одношаговый обработчик. Единая конвенция удешевляет навигацию и обзоры.

## Решение

Внутри `app/` держим слои по роли кода, а не по транспорту:

| Слой | Что там |
|------|---------|
| `Http` | Контроллеры, requests, middleware, resources — периметр сервиса |
| `Services` | Сценарии одного шага (use-case): создать заказ, зарезервировать остаток |
| `Saga` | Долгоживущие сценарии и их сообщения/конвертеры (Ecotone `#[Saga]`) |
| `Kafka` | Только адаптеры: обработчики входящих (`Handlers`), outbox-фабрики |
| `Messaging` | DTO/envelope интеграционных событий, если они не относятся к саге |
| `Models`, `DTO`, `Enums`, `Events`, `ValueObjects`, `Infrastructure` | Домен и технические детали |

Правило: **сага живёт в `App\Saga`, а не в `Kafka`/`Messaging`**. Транспорт (Kafka) вызывает обработчик, обработчик публикует шаг саги — сама сага не знает про Kafka.

Так сделано:

- catalog: `App\Saga\StockFulfillment`, шаги `ApplyStockStep`/`HoldStockStep`, `StockSagaMessage`, конвертер — перенесены из `App\Kafka\Saga`.
- order: `App\Saga\OrderFulfillment`, `OrderPlaced`, `FulfillmentEvents`, конвертер — перенесены из `App\Messaging`.

## Миграция постепенная

Полный переезд `app/` не делаем разом. Новый код кладём по конвенции сразу, старое двигаем при следующем касании файла. Шаблон слоёв для нового сервиса — [`docs/services/_skeleton.md`](../services/_skeleton.md).

## Почему так

Слой по роли (сценарий vs транспорт) переживает смену брокера: если завтра вместо Kafka появится очередь, `Services`/`Saga` не изменятся. Сага в `Kafka/Saga` смешивала жизненный цикл сценария с адаптером и мешала повторному использованию.

## Что отклонили

Полный DDD с `Domain`/`Application`/`Infrastructure` во всех сервисах сразу — слишком большой разовый рефакторинг для текущего объёма. Слой по типу сущности (`Order`, `Stock`) — дублирует домен и не отвечает на вопрос «где сага».
